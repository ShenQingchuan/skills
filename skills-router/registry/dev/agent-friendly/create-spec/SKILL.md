# Create Spec

本技能用于将当前会话中已经与用户探讨成熟的业务需求、产品方案或技术设计，直接结构化落盘为项目规范的 **Spec 目录**。

---

## 不要重新采访用户

**用户使用本技能时，往往已经在先前的对话中与你做了大量的讨论。**
- **默认行为**：直接从当前会话的上下文、讨论记录和代码现状中提取关键信息，组织成文并直接落盘。
- **严禁反向提问**：绝不要像面试官一样重新向用户掏出一大堆“请问你的背景是什么、目标是什么”等基础问题。
- **缺失信息处理**：如果确实发现某个致命细节未曾讨论，先根据最佳实践给出合理默认推导，在文末做简明标注，或做极简确认。

---

## 物理存储规范：一个 Spec 必须是一个独立目录

所有需求与方案必须以**独立目录**的形式存放在项目的 `.agents/specs/` 下：

**目录命名**：简明清晰，使用小写字母加连字符（如 `user-auth`、`refund-flow`、`01-core-pipeline`）。

```text
.agents/specs/<spec-name>/
├── README.md (或 spec.md) # 【必须】该需求的主方案说明
├── assets/                # 【可选】相关的原型截图、交互图或草图
└── examples/              # 【可选】接口样例数据、第三方响应示例等
```

---

## 内容结构规范：回答好两个灵魂问题

无论需求大小，生成的主方案文档（`README.md`）必须回答清楚两件事：

### 1. 事从何来？（背景与目标）
- **背景与痛点**：为什么要做这个？解决谁的什么问题？
- **核心目标与北极星**：做完这个需求，最关键的验收或衡量指标是什么？让后续干活的人和 AI 有明确的权衡锚点。

### 2. 如何做事？（流程、落地与验收）
- **用户的 Happy Path（黄金主路径）**：从头到尾讲透最理想、最常用的完整链路（用户从哪来、怎么操作、系统怎么响应、最终产出什么）。
- **关键边界与分支**：异常情况、空数据、网络失败、重复操作等常见边界的处理策略。
- **技术落地要点**：
  - 涉及改动或新增的核心模块与文件路径；
  - 关键数据结构、表字段或接口契约；
  - 架构决策记录（若有多种实现方式，明确写下“选了什么、放弃了什么、为什么这么选”）。
- **自测与验收路径**：如何验证这个需求已经保质保量做成了。

---

## 标准执行流程

1. **提取上下文**：梳理会话历史，提取出业务背景、达成的共识、流程细节与技术决策。
2. **确定目录名**：提炼一个语义清晰的英文小写目录名（如 `.agents/specs/<spec-name>/`）。
3. **组织与写入**：将主干内容写入 `.agents/specs/<spec-name>/README.md`。若讨论中附带了图片、JSON 数据等素材，同步归置到同级的 `assets/` 或 `examples/` 目录下。
4. **交付成果**：文件落盘后，告知用户落盘路径与核心概要，请用户审阅。
