# Manage Engineering

本技能用于管理项目的**工程实施过程**，帮助后续参与者从统一入口理解目标、当前状态、剩余风险和验证方式，而不是为每次提交建立实施日志。

---

## 一、先判断工作应该放在哪里

### 使用本技能

- 重构、架构迁移、依赖升级；
- 性能、稳定性、可观测性改造；
- CI、测试基础设施和内部工具调整；
- 用户无感知的技术缺陷修复；
- 产品需求下面较复杂、需要独立记录的技术实施工作。

### 不要使用本技能

关联产品 spec、能够独立验收的产品需求、功能或用户可感知缺陷，使用 `manage-project-kanban` 管理产品交付状态。

产品需求中的技术工作可以记录在 engineering 并关联产品卡片，但不得再拆成 Kanban 卡片。独立工程工作也不创建 Kanban 卡片。

一次性、低风险的小修改无需建立工程单元；代码、测试和提交历史已经足够。用户明确要求记录时除外。

---

## 二、先聚合，再决定是否新建

一个工程单元对应一个**可以独立闭环的工程目标**。同一单元可以包含多个实施步骤、代码模块和提交，也可以服务多个产品成果。

创建新单元前，先查看已有单元的 `README.md`。如果当前工作是在推进已有目标，直接续写原单元，更新其当前状态、技术方案与验证结果。

只有具备独立的目标、风险或验证闭环时，才建立并列单元。以下差异本身不构成新建理由：

- 同一工程目标下的前后实施步骤；
- 不同代码模块或提交；
- 同一产品卡片下的技术子任务；
- 文档变长或阶段性完成。

复杂单元在内部按技术主题拆文档，顶级目录仍保持同一个聚合入口。目录层级表达工程目标，不把纯分类目录或实施步骤提升为工程单元。

---

## 三、物理存储规范

每个工程单元使用一个独立目录，`README.md` 是唯一强制文件：

```text
.agents/engineering/
├── README.md                    # 可选：多个并行工程的导航
└── 001-unify-auth-flow/
    ├── README.md                # 必需：该工程目标的聚合入口
    ├── design.md                # 可选：复杂技术方案
    ├── verification.md          # 可选：详细验证记录
    └── assets/                  # 可选：图示、测量数据等
```

目录名使用三位数字前缀加小写英文短横线。新建前读取已有目录，在最大编号上递增，不复用编号，也不添加其他字母前缀。

编号只提供稳定标识和创建顺序，不表示优先级、依赖关系或实施步骤。一个编号覆盖一个聚合工程目标，单元内部步骤不占顶级编号。

存在多个并行工程时，可以在 `.agents/engineering/README.md` 维护轻量导航，只列进行中的单元及其当前焦点。详细状态仍以各单元入口为准，完成或中止后从该导航移除。

Agent 使用工程单元时先读 `README.md`，只有其中明确指向其他文件时才继续加载。

---

## 四、README.md 内容规范

简单工程单元可以只保留一个 README，不预先创建可选文件。主文档至少包含：

```markdown
# 001 统一认证流程

- 状态：draft | in_progress | done | abandoned
- 关联规格：`.agents/specs/...` 或无
- 关联产品卡片：无或卡片编号

## 目标与范围
为什么做，解决什么工程问题，明确不做什么。

## 工程全貌
主要阶段或组件之间的关系；当前所处阶段、剩余工作和下一步。
复杂细节链接到本单元内的主题文档。

## 技术方案
关键实现路径，以及需要保留的技术取舍。

## 风险与回滚
兼容性、迁移风险及回退方式。

## 验证
测试命令、验证结果和完成判据。
```

「工程全貌」是单元的聚合视图，使读者无需遍历子文档即可知道整体如何衔接、目前进行到哪里。它只维护工程实施状态，不复制 specs 中的产品流程和稳定契约。

更新进度时直接改写当前事实，保留未完成事项和阻塞点，不按时间顺序追加工作日志。已经完成的普通步骤由最终方案、测试和提交历史表达。

---

## 五、标准维护流程

1. **定位单元**：根据工程目标查找已有入口；可以续写时更新原单元，需要独立闭环时才分配新编号。
2. **写清闭环**：在 README 中明确目标、范围、风险、验证方式，以及各实施部分如何共同服务该目标。
3. **持续推进**：将状态改为 `in_progress`，维护工程全貌和当前进度。关联产品 spec 与产品卡片，但不复制产品交付状态。
4. **验证完成**：运行与改动相匹配的测试和实际场景验证，将结果写入 README 或本单元的验证文档。
5. **沉淀并退出**：把稳定产品行为和架构契约回写到 `.agents/specs/`，把长期约束回写到 `.agents/rules/`，把可重复验证尽量固化到测试，再将状态改为 `done`。
6. **精简保留**：清除失效计划、临时进度和重复契约。只有普通过程记录的单元可以删除；迁移回滚、重要技术取舍或难以复现的验证仍有长期价值时，保留精简后的最终结论与证据。
7. **中止工作**：保留中止原因和已经验证的结论，将状态标记为 `abandoned`，从进行中导航移除，避免后续重复尝试。
