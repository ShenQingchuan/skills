# Manage Engineering

本技能用于记录和管理项目的**工程实施过程**。它关注技术工作如何安全完成，不负责产品需求的排期、交付状态或产品验收。

---

## 一、先判断工作应该放在哪里

### 使用本技能

- 重构、架构迁移、依赖升级；
- 性能、稳定性、可观测性改造；
- CI、测试基础设施和内部工具调整；
- 用户无感知的技术缺陷修复；
- 产品需求下面较复杂、需要独立记录的技术实施单元。

### 不要使用本技能

如果工作本身是关联产品 spec、能够独立验收的产品需求、功能或用户可感知缺陷，应使用 `manage-project-kanban` 管理产品交付状态。

产品需求中的技术步骤可以记录在 engineering 并关联产品卡片，但**不得再拆成 Kanban 卡片**。独立工程工作也不创建 Kanban 卡片。

一次性、低风险的小修改无需强制建立工程单元；代码、测试和提交历史已经足够。用户明确要求记录时除外。

## 二、物理存储规范

每个工程单元必须是一个独立目录，且 `README.md` 是唯一强制文件：

```text
.agents/engineering/
└── 001-unify-auth-flow/
    ├── README.md          # 必需：工程单元入口
    ├── design.md          # 可选：复杂技术方案
    ├── verification.md    # 可选：详细验证记录
    └── assets/            # 可选：图示、测量数据等
```

目录名使用三位数字前缀加小写英文短横线，保证按目录排序即可看出创建顺序。新建前读取已有目录，在最大编号上递增，不复用编号，也不添加其他字母前缀。

Agent 使用工程单元时先读 `README.md`，只有其中明确指向其他文件时才继续加载。

---

## 三、README.md 内容规范

简单工程单元可以只保留一个 README，不预先创建可选文件。主文档至少包含：

```markdown
# 001 统一认证流程

- 状态：draft | in_progress | done | abandoned
- 关联规格：`.agents/specs/...` 或无
- 关联产品卡片：无或卡片编号

## 背景与目标
为什么做，要解决什么工程问题。

## 范围
做什么，以及明确不做什么。

## 技术方案
关键实现路径；复杂细节链接到 design.md。

## 实施清单
工程步骤和当前进度，不记录产品排期。

## 风险与回滚
兼容性、迁移风险及回退方式。

## 验证
测试命令、验证结果和完成判据。

## 完成记录
最终结论，以及需要回写到 specs 或 rules 的内容。
```

---

## 四、标准维护流程

1. **建立单元**：按下一个数字编号创建目录和 `README.md`，写清目标、范围、风险与验证方式。
2. **开始实施**：将状态改为 `in_progress`，在实施清单中记录真实进度。
3. **关联而不重复**：产品需求下的工程单元记录关联 spec 和产品卡片；不要在 Kanban 建立对应技术卡片，也不要复制产品状态。
4. **验证完成**：运行与改动相匹配的测试和实际场景验证，将结果写入 README 或可选的 `verification.md`。
5. **沉淀长期事实**：完成后把稳定的产品行为或架构结论回写到 `.agents/specs/`，把长期约束回写到 `.agents/rules/`，再将状态改为 `done`。
6. **中止工作**：不再实施的单元保留原因并标记为 `abandoned`，不要删除历史上下文。
